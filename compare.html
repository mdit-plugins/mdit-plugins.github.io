Methodology
  1. Correctness renders the same markdown with both implementations and compares the output byte for byte after a minimal normalization (attribute order; wrapper markup and generated ids only where both sides emit them by design). For variants without a custom renderer, the parsed token streams are compared as well — token metadata such as source maps is part of the public contract for plugins that build on top of these tokens. Every remaining difference is categorized as a reference error or an acceptable difference, grouped by root cause.
  2. Benchmark throughput and scaling numbers are medians of interleaved samples, so both sides run in the same process under the same load. Corpora are committed markdown files: normal is a realistic document with sparse syntax, heavy is dense plugin syntax; each is measured at three sizes.
  3. The test suite comparison runs each compared package's own unit tests against the reference implementation by swapping the built package entry for the reference package. Tests of features the reference does not provide are reported as feature gaps; tests that only assert internal implementation details are skipped silently and only counted in the aggregate; every other failing test is a behavior difference between the two packages.
  4. Each correctness difference is grouped under one root cause: "reference error" when the reference output or token stream is wrong (wrong source maps, missing or broken nesting, lost or misplaced content, security issues), and "difference" when the implementations merely represent the same result differently (equivalent token shape, alternative but valid output, intentional syntax or option design). Counts are per root cause, not per case.
  5. Scaling exponents are fitted on log-log axes: ~1 is linear and ~2 is quadratic. The series are built to expose the known superlinear paths of the reference implementations.
  6. Import cost is the gzipped size of the module graph reachable from the package's main entry (exports['.']): the entry file plus every relative import it loads, concatenated and gzipped as one stream, i.e. what a consumer downloads and parses when importing the plugin. Bare (peer) imports are not counted for either side. Comparing a single bundled file with an unbundled reference entry would understate the reference badly, so both sides are measured over the whole graph; the unpacked size of the published files is recorded in the committed data but not shown.
  7. Entry gzip is the gzipped size of the ESM entry: the resolved exports entry for the current package and the module / exports.import / main entry for the reference.

Tips

The comparison harness and the authored specs live in compare/. Run pnpm run compare to refresh the data, pnpm run compare:sizes to refresh the package sizes, and pnpm run compare:docs to regenerate this page's data.
